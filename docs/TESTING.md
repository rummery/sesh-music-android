# Validation

Validated with Flutter 3.47.7 / Dart 3.13.5 on the development VPS:

- `flutter analyze --no-pub`: **passed, no issues found**.
- `flutter test --no-pub`: **17 tests passed**.
- Android debug APK build: **passed**, minimum SDK 24 and target SDK 36.
  Manifest inspection confirms network/media-service permissions and disabled
  backup; APK bytecode contains the custom `AudioServiceActivity` integration.
- Initial `flutter build web --release --base-href /mobile/`: **passed**,
  including the WebAssembly compatibility dry run. The deployed release is rebuilt
  with local web resources and `--no-wasm-dry-run` after that compatibility check.

Focused automated coverage:

- Subsonic token derivation and fresh request salts; password never placed directly
  in request parameters.
- Same-server media-path validation, external-host rejection, configured base paths
  included once, structured errors and proxy error-body redaction.
- Idempotency key persistence across uncertain creation failures.
- Account changes while an idempotent mutation is pending abort before any HTTP
  write; a late login response cannot overwrite the latest account/preferences.
- Opaque track identity, milliseconds and separate repeated-playlist-entry identity.
- Native partial-file HTTP Range resume, replacement when a server returns a full
  response, size/checksum verification, cancellation, incomplete-file exclusion and
  successful offline file reopening through a new storage instance.
- A widget check for the acquisition-first offline-download explanation.

Tests use generated byte fixtures for transfer/storage and mocked HTTP responses for
request behavior. These do not establish live upstream availability, Android audio
decoding, background execution, notification controls or physical-device behavior.
Real server/browser and Android build checks are documented with the server delivery.

Browser integration checks use the compiled Flutter release and a real isolated Go
server/database with generated MP3 audio. Authentication, search, actual playback
and pause, permanent server acquisition and IndexedDB storage passed. Offline Blob
playback advanced its audio clock with all REST requests blocked. Desktop and phone
screenshots were captured; the public HTTPS phone preview loaded its connection
form without creating a production account or logging in.

Required physical-device follow-up:

1. Connect to the HTTPS server with a normal user, browse all four search types and
   play both a library track and an upstream track.
2. Lock the screen, use notification/headset next/previous, change audio focus and
   test a phone-call interruption.
3. Download a track, interrupt connectivity, reopen and retry; verify it plays in
   airplane mode after restarting the app.
4. Switch accounts and confirm that offline files, active transfers, playlists and
   jobs are scoped to the correct account.
5. Check vendor battery restrictions. There is no OS-scheduled download service;
   native partials resume when the app process is running again.
